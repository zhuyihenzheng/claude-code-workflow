# 機能マップの作成と更新

機能マップは、人とエージェントが同じ名前で画面と機能を呼ぶための共通の語彙であり、各機能を実際に動かして証跡を残すための手順書である。「左のサイドバーのあれ」と言われて推測する必要をなくし、レビューを diff の通読から証跡の確認に移す。

書式は `docs/feature-map/README.md` に従う。1 機能 1 ファイルとし、ファイル名は `<機能ID>-<英小文字の短い名前>.md` とする。

## 1. リポジトリから調べる

ユーザーに聞く前に、コードと資料から次を調べる。観察できないことだけを確認する。

- **機能と ID**：設計書の画面一覧（画面 ID があればそれを機能 ID にする）、Controller の `@GetMapping` / `@PostMapping`、メニューの JSP、`screen-tests/cases.mjs` のスイート。
- **到達方法**：メニューからの経路、URL、必要なログイン状態と権限。
- **動かし方**：`scripts/htmx-check.mjs` のコマンド、`screen-tests/` のスイート（`node run.mjs --engine playwright --only <スイート>`）、MockMvc では確認できない画面の操作。
- **前提データ**：合成データのテストアカウントの入手先、初期データの投入方法。実際の認証情報は書かない。

最初は利用頻度または変更頻度の高い 3〜5 機能から作る。

## 2. 機能ファイルを書く

README の「機能ファイルの書式」の 4 つの節を、この順で書く。

- コマンドは、このリポジトリで実際に動くものをそのまま書く。セレクターは id、label、ARIA ロールなど変わりにくいものを使い、画面上の位置や順番に頼らない。
- 合否は、操作の結果として利用者に見える状態（表示される文言、置換されたフラグメント、保存された値の再表示）で判断する。「保存しました」の表示だけでなく、再表示で値を確認する。
- 前提データが足りずに確認できない手順は、手順を弱めずに「注意点」に理由を書き、確認できなかったと報告する。

## 3. 1 機能を実際に動かして証明する

- アプリケーションを起動し、作成した機能ファイルのうち 1 つの手順をすべて実行する。証跡（スクリーンショット、コマンドの出力）が README に書いた保存先に残っていることを確認する。
- 失敗した場合は、手順またはアプリケーションの起動方法を直して再実行する。一度も実行していない手順は下書きであり、完成として報告しない。

## 4. 変更のたびに更新する

- 画面や操作を変更した PR では、同じ PR で該当する機能ファイルを更新する。新しい画面は機能ファイルを追加する。
- 機能マップの手順が失敗した場合は、アプリケーションの不具合か、機能マップが古いのかを切り分ける。機能マップが古い場合は、実際の画面に合わせて直す。期待値を実装に合わせて弱めない（期待値の根拠は設計書）。

## 報告

作成・更新した機能ファイル、実際に動かした機能と証跡の保存先、確認できなかった手順とその理由を報告する。
