# 改修の標準手順

設計書を先に直し、そこから期待値を取る。実装に合わせて設計書や期待値を後から書き換えると、不具合が「仕様」になる。各ステップの完了条件を満たしてから次へ進む。

## 1. 変更点の確定

- 依頼の言葉を `docs/knowledge/glossary.md` で画面の項目名・コード上の名前に置き換え、`docs/knowledge/codemap.md` で関係するファイルを引く（ない場合はコードから探し、6 で書き戻す）。
- 依頼内容に対応する設計書の箇所を特定する。Excel 設計書は `specs-ai/index.md` から必要なシートの Markdown（`sheets/<シート>.md`）だけを読む。Markdown の設計書は直接読む。
- 「設計書のどの項目が、何から何に変わるか」を一覧にする。画面、入力チェック、メッセージ、業務ルールの境界値を漏らさない。
- 設計書に記載がなく判断できない点は、推測せずユーザーに確認する。

完了条件：変更点の一覧をユーザーに提示し、了承を得ている。

## 2. 設計書の修正

- **Markdown の設計書**：直接編集する。
- **Excel の設計書**：直接編集しない。変更指示（JSON）を `specs/changes/<案件名>.json` に書き、次を実行する。

  ```bash
  python scripts/xlsx_patch.py apply specs/<ブック>.xlsx specs/changes/<案件名>.json --dry-run   # 変更されるセルを確認
  python scripts/xlsx_patch.py apply specs/<ブック>.xlsx specs/changes/<案件名>.json
  python scripts/xlsx2ai.py                                                                    # specs-ai/ を再生成
  ```

  変更指示は、セル番地 + 現在の値（`from`）、または「見出しの列名 + キー列の値」で書く。行番号を数えて指定しない。表に行を足す場合は `table.append` に書く（表の直下の空き行に、最後の行の書式で書かれる。空き行がなければ止まるので、人に Excel での行の挿入を依頼する）。書式は `scripts/xlsx_patch.py` の冒頭に記載している。スクリプトがエラーで終了した場合は、何も書き込まれていない。指示を直して再実行する。
- 人が Excel で直接修正した場合は、`python scripts/xlsx_patch.py diff <修正前> <修正後> --expect <変更指示>` で、指示以外のセル・書式・画像が変わっていないことを確認する。NG が出た場合は内容をそのまま報告し、問題なしと判断しない。

完了条件：設計書が変更点の一覧どおりになっており、`--dry-run` の出力（または diff）をユーザーに提示している。

## 3. 単体テストと実装

- 変更後の設計書に基づいて単体テストを先に修正・追加し、想定した理由で失敗することを確認する。
- 実装する。タスクに関係しない箇所は変更しない。
- `./mvnw -Dtest=<TestClass> test` が成功することを確認する。テストには `@DisplayName` で、設計書のどの項目を確認するかを書く。
- 設計書の表とコードの値の対応が `config/spec-sync.json` に登録されている場合は、`python scripts/spec_sync.py` が終了コード 0 になることを確認する。メッセージ一覧のように設計書とコードで同じ値を持つ表を新しく変更した場合は、対応を登録する。

完了条件：関連テストと `spec_sync.py` が成功し、実際のコマンド出力を提示している。

## 4. 画面試験

画面の表示・入力チェック・メッセージ・遷移が変わる場合に実施する（`screen-tests/`。未導入の場合は `scripts/htmx-check.mjs` で変更箇所を確認し、その旨を報告する）。

1. `screen-tests/cases.mjs` の該当ケースを修正・追加する。期待値は設計書の記述から取り、画面に表示された値を写さない。ケース ID は変更しない。
2. `node run.mjs --engine playwright --build-only` で、ケースの書き方を確認する。`観点カバレッジ.md`（設計書の項目にケースがあるか、根拠のない期待値がないか）は `site.mjs` の `design` に指定した Markdown から生成される。Excel の設計書は `xlsx2ai.py` が生成した `specs-ai/<ブック>/sheets/<シート>.md` を指定する。生成された観点カバレッジで、変更点の一覧とケース ID の対応を確認する。
3. アプリケーションを**変更後のコードで**起動し直してから、`node run.mjs --engine playwright` を実行する（`screen-tests/` で実行）。
4. `結果一覧.md` を読む。`report.html`、`試験結果.xlsx`、`evidence/` の画像は人が見るためのものであり、読み込まない。
   - NG（実行不能）・ブロック：ケース、辞書、待機条件を直して再実行する。
   - NG（不一致）：設計書どおりでない挙動である。実装を直す。設計書が誤っている場合は 1 に戻る。
   - 期待値の変更、`baseline.json` への登録、`health.ignore` の追加で結果を OK にしない。`baseline.json` を更新できるのは人だけである。

完了条件：変更した画面のケースが設計書どおりの期待値で OK になっており、想定外の NG がない。残った NG は `不具合票ドラフト.md` の該当箇所とともに報告している。

## 5. 試験書の更新

- `試験仕様書.xlsx` と `試験結果.xlsx` は `cases.mjs` と実行結果から生成される。手で編集せず、4 の実行で生成されたものをそのまま使用する。
- 試験結果に備考（票番号、確認者のコメントなど）を追記する場合は、2 と同じく `scripts/xlsx_patch.py` の変更指示で行う。キー列は「ケースID」を使用する。

- 単体テストの成績書は、`./mvnw test`（または verify）の後に `python scripts/junit_report.py` で作る（`target/test-report/単体テスト成績書.md` / `.xlsx`）。手で編集しない。提出する版は、最後のコミットで実行したものにする。

完了条件：コミット対象に、設計書・変更指示・`cases.mjs`・生成された試験仕様書が含まれている。単体テスト成績書を作成し、出力先を報告している。

## 6. レビューと報告

- `./mvnw verify` と `python scripts/guard.py` を実行する。
- 画面の操作や表示を変えた場合は、`docs/feature-map/` の該当する機能ファイルを同じ変更で更新する。
- `knowledge` skill で、今回確かめた用語・場所・注意点を `docs/knowledge/` に書き戻し、`python scripts/knowledge_check.py` を実行する。
- `REVIEW.md` の基準でレビューを受ける（Claude Code では code-reviewer サブエージェント、GitHub Copilot ではコードレビュー）。比較元のコミット、diff、変更点の一覧、テスト結果、guard の出力、`結果一覧.md` のパスを渡す。
- 報告には、変更点の一覧、修正した設計書の箇所、追加・修正したテストとケース ID、各コマンドの結果、単体テスト成績書の出力先、書き戻した知識、未実施の検証とその理由を含める。
