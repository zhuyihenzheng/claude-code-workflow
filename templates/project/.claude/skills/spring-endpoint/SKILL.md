# エンドポイント追加の標準手順

以下の順序で実施し、各ステップの成果物を明確にする。ステップを省略しない。

## 1. インターフェース仕様の確認

- 入力／出力、HTMX フラグメント版の要否、権限要件を確認する。不明点は先に確認し、推測で進めない。
- 既存の実装例を参照する：`<!-- TODO プロジェクト内の参考となる Controller のパスを記載する -->`。

## 2. テストの先行作成（Red）

- Service 層の単体テストを作成する（JUnit 5 + Mockito）。
- Controller 層は MockMvc でインターフェース仕様のテストを作成し、ステータスコードと主要なレスポンス内容をアサーションで確認する。
- テストを実行し、想定した理由で失敗することを確認する：`./mvnw -Dtest=<TestClass> test`。

## 3. 実装（Green）

- DTO → Service → Repository（必要な場合）→ Controller の順に実装する。
- コンストラクタインジェクションを使用し、DTO でエンティティをそのまま公開しない。例外は共通の例外処理に委ね、個別に握りつぶさない。

## 4. 画面の実装（HTMX/JSP を使用する場合）

- 画面全体とフラグメントのエンドポイントを分ける。`hx-target` には存在する id を指定する。フォームの入力チェックエラーに 422 を使用する場合は、共通レイアウトに 422 の swap が設定済みであることを確認し、フラグメントの再表示を検証する（HTMX はデフォルトで 422 を置換しない）。
- JSP では scriptlet の新規追加を禁止し、出力をエスケープする（.claude/rules/ を参照）。

## 5. 検証（すべて必須の完了条件）

- `./mvnw -Dtest=<TestClass> test` が成功したことを確認し、出力を提示する。
- `./mvnw -q compile` が成功することを確認する。
- 画面を含む場合：サービス起動後、ブラウザーで画面を開いて実際に操作し、フラグメントの置換成功をアサーションで確認してスクリーンショットを保存する。
- 最後に code-reviewer サブエージェントで diff をレビューしてから、結果を報告する。
