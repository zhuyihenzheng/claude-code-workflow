# レビュー基準

人、Claude Code の `code-reviewer` サブエージェント、GitHub Copilot のコードレビューが共通で使う確認の順序と観点である。プロジェクトルールの正本は `AGENTS.md` であり、ここでは PR をどの順で、何を根拠に確認するかだけを定める。

## 確認の順序

証跡から始め、diff はそれを裏付けるために読む。

1. **検証の証跡**：PR 本文に、実行したコマンドと結果があるか（`python scripts/guard.py`、`./mvnw verify`）。画面の変更には、`docs/feature-map/` の該当機能の手順を実行した結果とスクリーンショット（または画面試験の `結果一覧.md`）があるか。「確認しました」という記述だけの場合は証跡なしとして扱う。guard の出力がない、または NG の場合はマージ不可とする。
2. **正確性**：設計書と受入基準を満たしているか。境界値と例外経路、null、並行処理、トランザクション境界に問題がないか。
3. **プロジェクト規約**：レイヤー構成（Controller → Service → Mapper/Repository）、コンストラクタインジェクション、DTO がエンティティをそのまま公開していないこと、共通の例外処理に従っていること。
4. **テスト**：新しいロジックにテストがあるか。実行が成功するだけでなく、振る舞いをアサーションで確認しているか。結合テストの経路で重要な部分を mock に置き換えていないか。
5. **画面（HTMX/JSP）**：scriptlet を新規追加していないか。出力をエスケープしているか。`hx-target` の対象が存在するか。ブラウザーでの検証の証跡があるか。
6. **セキュリティ**：インジェクション、権限逸脱、ログへの機密情報の出力、未検証の外部入力がないか。
7. **例外とコメント**：新しい `guard:allow`、`config/guard/baseline.json` の件数の増加、`config/guard/rules.json`・`config/pmd/`・`src/test/java/ArchitectureTest.java` のルールの削除や緩和はマージ不可とし、人の承認が必要と明記する。回避策を正当化するコメント、コメントアウトしたコードは要修正とし、根本原因の直し方を示す。
8. **再発防止の候補**：`AGENTS.md` に書かれているのに守られていない規約、または diff の中で同じ種類の指摘が繰り返し出る場合は、改善提案として guard のルール案（id、対象ファイル、pattern、message）を示す。

## 報告の形式

重大度別（マージ不可／要修正／改善提案）に分類し、各項目にファイル:行番号、問題点、根拠（規約の参照先または設計書の該当箇所）を記載する。問題がなければ「マージを妨げる問題は見つかりませんでした」と明記する。件数を増やすために、好みの範囲のスタイルを指摘しない。必要な入力（diff、証跡）が揃っていない場合は「レビュー未完了」と明記し、すべての変更を確認済みと報告しない。
