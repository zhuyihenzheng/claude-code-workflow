# 01 · 总体规划

## 目标

让 Claude Code 从"个人玩具"变成团队可复用、可验证、可控成本的开发基础设施。衡量标准不是"AI 写了多少代码"，而是：

- **交付回路可判定**：每个任务都有机器可判定的完成标准（测试转绿、构建通过、页面行为断言通过），而不是靠人眼通读 diff；
- **知识沉淀在仓库里**：项目事实写进 `CLAUDE.md` / rules / skills，随 git 版本管理，新成员 clone 即得；
- **强制规则机器执行**：安全与规范红线由 hooks / permissions / 沙箱强制，不靠提示词自觉；
- **成本可见可控**：模型路由有默认，用量按周复盘（`/usage`），无人值守任务有预算上限。

## 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  开发者表面：CLI（全功能） / IntelliJ 插件（Java 团队主力）   │
│              VS Code 扩展 / Desktop（并行会话）               │
├─────────────────────────────────────────────────────────────┤
│  指令层（非强制，靠上下文）                                   │
│  CLAUDE.md（<200 行） · .claude/rules/（路径作用域）          │
│  Skills（按需加载的流程） · Subagents（独立上下文的角色）     │
├─────────────────────────────────────────────────────────────┤
│  执行层（依赖配置与运行边界）                                   │
│  Hooks（格式化/编译/拦截） · Permissions allow/deny           │
│  Sandbox（Bash 文件/网络限制） · Managed settings（组织下发） │
├─────────────────────────────────────────────────────────────┤
│  工具层：MCP（Context7 / Playwright / DBHub / GitHub）        │
│          LSP 代码智能插件（Java: jdtls-lsp） · gh CLI         │
├─────────────────────────────────────────────────────────────┤
│  协作层：GitHub App（@claude） · 官方 Code Review             │
│          claude-code-action（CI 自动化） · Headless 脚本      │
└─────────────────────────────────────────────────────────────┘
```

分层原则：指令表达意图，hooks 和权限规则提供可执行的检查，OS 隔离与凭据权限限制进程能力，CI/分支保护决定能否合并。每层都有作用范围，不能互相替代。

## 分阶段路线图

### 阶段 0 · 准备（第 1–2 天）
- 全员安装 Claude Code CLI + IntelliJ 插件（JetBrains 插件是在 IDE 终端里跑 CLI + diff 查看器，Java 团队走这条线）；
- 统一订阅/账号口径，确认 `/model` 里实际解析到的模型版本；
- 仓库初始化 `.claude/` 骨架（见 [templates/](../templates/)）。

### 阶段 1 · 基础（第 1 周）
- 用 `/init` 生成 CLAUDE.md 初稿，然后**主要工作是删行**：只保留命令、版本、仓库外决策、被纠正过的坑，目标 <200 行；
- `.claude/settings.json` 提交入库：权限 allowlist（构建、测试、git 只读类）、deny `.env` 与密钥文件；
- 确立单一事实源：构建 `./mvnw`、单测、起服务、页面验证命令全部写进 CLAUDE.md。

### 阶段 2 · 验证回路与工具箱（第 2 周）
- 装官方 `jdtls-lsp` 插件（Java 符号导航 + 编辑后诊断）；团队成员本机需有 jdtls 可用；
- MCP 默认 Context7（查文档）与 Playwright（浏览器验证）；DBHub 和 GitHub 按需启用，已有 `gh` CLI 时不必重复安装；
- 按项目配置 formatter/check；Stop hook 做有超时与失败出口的编译反馈，CI 做最终门禁；
- HTMX/JSP 改动固定回路：`改代码 → 起服务 → Playwright 脚本或 MCP 打开页面 → 截图/断言 → 才算完成`。

### 阶段 3 · 团队化（第 3–4 周）
- `/install-github-app` 接入 GitHub App：issue/PR 里 `@claude` 触发小修；开启官方 Code Review 做 PR 初审；
- 把重复出现的多步流程沉淀为项目 skill（目标 2–3 个，如"新增 Spring 接口"、"JSP 页面改造"）；
- 每周检查实际可用的用量统计与账单，据此定模型路由默认值，而不是照抄社区口径。

### 阶段 4 · 进阶（按需，不设时间表）
- 并行任务用原生 `claude --worktree <name>` 多会话并行，各自开 PR；
- 机械性大改用 `/batch`（拆 5–30 个单元，每单元一个 worktree + PR）；
- 定时/批处理用 headless `claude -p --bare` + `--max-budget-usd` 写脚本进 CI；
- 全库审计类任务再考虑动态工作流（大量 subagent 交叉核验）。

## 模型路由（默认策略）

以下是按任务复杂度选择的起点，不是性能基准；可用模型、别名解析与 effort 选项以 `/model` / `/status` 和官方文档为准：

| 场景 | 模型 |
|---|---|
| 日常计划（Plan Mode） | `opusplan`（计划用 Opus、执行切 Sonnet）或团队默认 |
| 日常编码默认 | 团队可用的中档模型起步，以实际质量、耗时与成本评估 |
| 疑难根因 / 架构决策 / flaky 测试 | 团队可用的强模型 + 支持的较高推理设置 |
| 探索、格式化、简单 subagent | 在 subagent 定义里钉 `model: haiku` |
| 快速来回的小改 | `/effort low`；单条消息加压用 `ultrathink`（只在当前模型支持时使用） |

⚠️ 别名陷阱：Bedrock / Vertex / Foundry 上 `sonnet`、`opus` 等别名可能解析到旧版本。走云厂商接入时必须用完整 model ID 钉死，并在 `/status` 里核对。

成本纪律：无人值守/脚本化一律带 `--max-budget-usd` 或 `--max-turns`；MCP 只装在用的（工具发现与缓存机制影响实际开销，使用 `/context` 与账单测量）；能用 CLI（如 `gh`）就不用 MCP。
