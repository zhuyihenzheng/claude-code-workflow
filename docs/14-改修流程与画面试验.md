# 14 · 改修流程：设计书 → 实现 → 测试 → 画面试验 → 试验书

一次改修要动四样东西：设计书、代码、测试、试验书。模板把它们串成一条流程，放在 skill [`change-flow`](../templates/project/.claude/skills/change-flow/SKILL.md) 里。顺序是固定的：**先改设计书，期待值从设计书取**。反过来做，不具合就会被写成“仕様”。

```
1. 确定变更点      设计书哪一项、从什么改成什么（用户确认）
2. 改设计书        Markdown 直接改；Excel 写变更指示 → xlsx_patch.py 应用 → xlsx2ai.py 重新生成
3. 单体测试 + 实现  先红后绿，./mvnw -Dtest=… test
4. 画面试验        改 cases.mjs（期待值来自设计书）→ run.mjs --build-only → 重启应用 → run.mjs → 读 結果一覧.md
5. 试验书          試験仕様書.xlsx / 試験結果.xlsx 由运行生成；备注用 xlsx_patch.py 追加
6. 评审与报告      ./mvnw verify → code-reviewer → 报告
```

## 1. 画面试验：整合 midscene-poc

[midscene-poc](https://github.com/zhuyihenzheng/midscene-poc) 是画面试验框架：一份 `cases.mjs` 同时生成试验仕样书、执行浏览器操作、按设计书判定、和基准比较，并输出试验结果与证迹。默认用 Playwright 引擎，不需要 AI 模型。

整合方式是把它作为依赖装进应用仓库的 `screen-tests/` 目录，固定到提交 SHA。这样用例和应用代码在同一个仓库、同一个 PR 里变更。

```bash
python3 scripts/install.py project /path/to/your-project --with-screen-tests --apply
cd /path/to/your-project/screen-tests
npm install
npx screen-test-new-site <系统名> --dir . --url http://localhost:8080/
```

`観点カバレッジ.md`（设计书的画面、消息有没有对应用例）读取 Markdown 设计书。Excel 设计书由 `xlsx2ai.py` 转成 `specs-ai/<书>/sheets/<sheet>.md`（表格还原为 Markdown 表），把它指定给 `site.mjs` 的 `design` 即可得到同样的检查；示例应用的端到端测试用 Excel 版设计书验证了这一点，见 [11 · Excel 设计书](11-Excel设计书.md)。

之后的日常命令、结果怎么读，见装进去的 [`screen-tests/README.md`](../templates/project/screen-tests/README.md)（日文）。用例的写法规范在框架里，模板只指向它，不复制。

### 和 `htmx-check.mjs` 的分工

| | `scripts/htmx-check.mjs` | `screen-tests/`（midscene-poc） |
|---|---|---|
| 用途 | 开发中确认**一次交互**（片段有没有被替换） | 按设计书对画面做**回归试验** |
| 输入 | 命令行参数 | `cases.mjs`（期待值来自设计书） |
| 输出 | 退出码、一张截图 | 试验仕样书、试验结果、证迹、JUnit XML、缺陷票草稿 |
| 何时用 | 改 HTMX 片段时随手验证；没有导入画面试验的项目 | 画面的显示、输入检查、消息、迁移有变化时；CI |

### 这补上了控制矩阵里最大的缺口

此前“页面改动是否在浏览器里验证过”在会话之外没有任何证明。导入画面试验后：`cases.mjs` 进仓库，CI 运行它并产出 `out/junit.xml` 与 `試験結果.xlsx`，NG 与基准不符时命令以失败结束。CI 示例里有对应的 job（默认注释）。

### 权限上的处理

- `node run.mjs --engine playwright`（含 `--build-only`、`--only`）预先允许。
- `--engine ai`、`--engine midscene`、`--heal`、`--ai-assert` 会把画面截图发给模型，设为 ask。
- `--update-baseline`、`--update-visual` 只能由人执行，设为 deny；`baseline.json` 的编辑设为 ask。
- 内嵌截图的 `report.html` 禁止读取。AI 读 `結果一覧.md`；`試験結果.xlsx` 本来就被 xlsx 的 deny 挡住。

## 2. 改 Excel：AI 只写变更指示，脚本负责写入和核对

让 AI 通过 Excel MCP 直接改工作簿并不可靠。在一份带 42 张截图的试验结果上做过的实测里，写错行、多建空格子、图片整批丢失都出现过，而且模型每次都报告“已确认”。所以模板的做法是把“判断改什么”和“动手写”分开：

- **AI 写变更指示（JSON）**：用“单元格 + 当前值”，或“表头列名 + 键列的值”来指定位置，不写行号。
- **[`xlsx_patch.py`](../templates/project/scripts/xlsx_patch.py) 负责写入**：只改指示里的单元格所在的那一个 sheet XML，其余文件（图片、样式、其他 sheet）原样复制。保存前自己核对“只有指示的单元格变成了指示的值”，不符就什么都不写。
- **同一个脚本负责核对人的修改**：`diff --expect` 比较修改前后的两个工作簿，指示之外的单元格、样式、图片有变化就让命令失败。每次保存都会变的内容不参与比较：更新时间等元数据、计算链、共享字符串的排列、样式表的编号、选中的单元格与缩放与滚动位置、当前 sheet、`[Content_Types].xml` 与关系文件的排列顺序。sheet 除单元格外还比较列宽、合并、冻结窗格、筛选、数据验证、条件格式、超链接、保护、分页、图形的引用；工作簿比较 sheet 名与隐藏状态、名称定义。样式按字体、填充、边框、显示格式的实际定义来比。

```json
{"sheet": "試験結果",
 "table": {"key": "ケースID", "add_columns": ["備考"],
           "rows": {"C-01": {"備考": "既知 NG：#123"}}}}
```

```bash
python scripts/xlsx_patch.py apply specs/設計書.xlsx specs/changes/案件.json --dry-run
python scripts/xlsx_patch.py apply specs/設計書.xlsx specs/changes/案件.json
python scripts/xlsx_patch.py diff  修改前.xlsx 修改后.xlsx --expect specs/changes/案件.json
```

拒绝写入的情况：当前值与 `from` 不一致、键匹配到 0 行或多行、列不存在、公式单元格、合并单元格的非左上角。遇到任何一条，整份指示都不执行。

限制：只写字符串（换行统一为 LF，Excel 存不了的控制字符直接拒绝）；新建的单元格不带样式；不处理图形和图表里的文字。结构性的修改（插入行、调整合并）仍然要人在 Excel 里做，然后用 `diff --expect` 核对。

## 3. 验证范围

| 已验证 | 未验证 |
|---|---|
| 示例应用（Spring Boot + JSP + HTMX）上：安装模板 → 从 GitHub 按 SHA 安装框架 → `npm run build` → 实际运行 3 个用例全部 OK → 故意改错期待值时以失败结束（CI） | 真实业务项目上的画面试验（登录、数据初始化、老式画面） |
| `xlsx_patch.py`：合成工作簿的单元测试（含模拟“再保存”后元数据、样式表、视图状态、`[Content_Types].xml` 顺序变化的情况，以及其他工具写出的、行没有 `r` 属性或属性换行的 sheet）；框架实际输出的、带 25 张截图的试验结果上，按 ケースID 写备注后图片逐字节一致 | 用 Excel 桌面版实际打开、编辑、保存后的工作簿：`apply` 的结果能否正常打开、`diff --expect` 会不会误报，都没有用真实的 Excel 验证过 |
| 权限规则的写法（按文档语义自行匹配） | 这些规则在 Claude Code 会话里的实际效果 |
| | `change-flow` skill 在真实改修任务上的表现：尚未跑过一次完整流程 |

框架和 Playwright 都固定了版本。升级时改 `screen-tests/package.json`，并让示例应用的端到端检查通过。当前固定的 SHA 是 midscene-poc `main` 历史上的一个提交（zhuyihenzheng/midscene-poc#2 以合并提交方式并入）。

装进导入方项目的 `screen-tests/package.json` 和 README 里写着框架所在的 GitHub 账号名。
