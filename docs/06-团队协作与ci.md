# 06 · 团队协作与 CI

## 1. `.claude/` 入库规范

- 入库：`CLAUDE.md`、`.claude/settings.json`、`.claude/rules/`、`.claude/agents/`、`.claude/skills/`、`.mcp.json`（密钥用环境变量引用）；
- 不入库：`.claude/settings.local.json`（个人覆盖）、任何含真实 token 的文件；
- 这些文件走正常 PR 审查：改 CLAUDE.md / hooks / 权限等于改全团队的 AI 行为，按代码同等对待；
- 新成员 onboarding：clone → 装 CLI/插件与 jdtls → `/doctor` 体检 → 按 CLAUDE.md 里的命令跑通一次构建与测试 → 用 Plan Mode 完成一个小任务。

## 2. GitHub 集成三件套

| 方式 | 适合 | 说明 |
|---|---|---|
| GitHub App（`@claude`） | issue/PR 评论里触发小修、答疑、改文档 | `/install-github-app` 一键安装并生成 workflow；触发者须有写权限，默认拒绝 bot 触发 |
| 官方 Code Review 产品 | 每个 PR 自动初审 | 无须自己写 workflow；在人审之前先过一遍 AI，分级输出问题 |
| `anthropics/claude-code-action@v1` | 定时/事件驱动的自动化（批量修复、依赖升级、文档同步） | 构建在 Claude Agent SDK 上；脚本化任务遵守 [03](03-标准工作流.md) 的无人值守五问 |

GitLab 团队：官方另有 GitLab CI/CD 集成页，思路相同。

## 3. AI 代码的 review 政策（建议）

- AI 生成的代码与人写的代码**同一标准**合并，不降低门槛；作者对提交的代码负责，禁止"AI 写的"式免责；
- PR 描述必须带验证证据：跑过的测试与输出摘要、页面改动的截图（HTMX/JSP 必备）；
- 高风险区（支付、权限、数据迁移、JSP 老页面大改）强制人审 + reviewer 子代理双过；
- 用 `/code-review` 或官方 Code Review 做初审，人审聚焦设计与业务正确性，不再耗在格式与低级错误上（那些交给 hook 与 linter 在提交前拦掉）。

## 4. 成本治理

- 每周固定看一次 `/usage`：按 skill / subagent / MCP 分项找大头；社区与官方口径有分歧时（官方默认 Opus、社区默认 Sonnet），以自己团队四周数据裁决默认模型；
- 无人值守与 CI 任务一律设 `--max-budget-usd` / `--max-turns`，组织层可设 spend limit；
- 上下文卫生：不相关任务 `/clear`、长会话适时 `/compact`、探索类活儿派 haiku 子代理，主会话保持干净；
- 警惕"省 token 工具"的营销数字：有独立基准（约 $1,500 实测）显示某些代理类省钱工具账单并未下降（见 [07](07-避坑清单.md)），引入前用 ccusage 做前后对照。

## 5. 安全清单

- [ ] `permissions.deny` 覆盖 `.env*`、密钥/凭据文件，且知道 deny 在所有权限模式（含 bypass）下生效
- [ ] 危险 Bash 命令在 deny/沙箱策略内；生产环境操作不走 AI 会话
- [ ] `/sandbox` 已开启并理解其边界：**只覆盖 Bash，文件工具与 MCP 在沙箱外**
- [ ] MCP 只连开发/测试环境；数据库只读账号；凭据走环境变量且作用域最小
- [ ] Playwright/浏览器类工具用隔离 profile，不连生产
- [ ] 第三方插件/skill/mod 安装前过目代码来源；mods 只用官方内置（见 [05](05-工具箱.md)）
- [ ] GitHub App 触发权限收紧（须写权限、拒绝 bot 触发）；CI 里的 API key 用仓库 Secret 且设预算上限
- [ ] 敏感项目评估 managed settings（组织统一红线，下层不可覆盖）
