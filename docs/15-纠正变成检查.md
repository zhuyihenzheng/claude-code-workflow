# 15 · 把纠正变成检查：「All Code Is Slop (Except Mine)」的质量架构

Lauren Tan（poteto，SpaceXSI / xAI 的 Grok Bot 客户端团队，React 核心团队成员）在 AI Engineer Code Summit（2026-11-11，旧金山，主会场）的演讲。本页先讲她说了什么，再讲本仓库据此搭了什么、刻意没搭什么。

依据与边界：演讲内容取自现场录音的机器转写稿（部分词被误识，例如性质测试库 Bombadil 被转成 “Duckbill”），并与她开源的 pstack skills（[cursor/plugins](https://github.com/cursor/plugins/tree/main/pstack)，MIT）交叉核对。会后几篇解读文章因本环境网络限制未能读取。她给出的数字是自述，本手册没有独立核实。

## 一句话

标题里的 “mine” 指的不是她自己写的代码，而是她为 agent 准备的环境：**每纠正 agent 一次，就把它变成一条确定性检查，或者用更好的 API 与架构让这类错误无从发生**；评审从通读 diff 变成查看验证证据。在这之前就去自动化，只会把产出 slop 的回路放大成产出更多 slop。

## 她报告的结果（自述）

| 指标 | 数字 |
|---|---|
| 个人上个月合入生产的 PR | 约 3,000 |
| 团队 PR | 11,000；10 月有 227 人至少提交过 1 个 PR，其中很多是缺少上下文的顺手贡献者 |
| 发版 | 约每天一个稳定版 |
| 被 revert 的 PR 比例 | 相对值在下降，稳定在约 0.5% |
| 性能 | 启动、输入、打开与切换对话都比上线时更快（仍是 Electron 应用） |
| 代价 | 她用了 6 个月才走到可以信任 agent 的程度 |

她的论点：有了 agent，人人都能成为“编码机器”；工程师真正的工作变成了**在产量大幅提高的同时，维持甚至提高代码质量**。她不叫它“软件工厂”，而是叫“信任”——不是盲目信任，而是投资 agent 的环境，让你可以相信它默认会做对。

## 核心模型：倒置的信任金字塔

金字塔是倒着放的：越靠上越宽，代表越值得投入。上两层是确定性的，用来约束 agent、让它默认做对；第三层用来找 bug、检查不变式、检查 agent 是否理解了意图；文字只放在最底下，留给需要判断的事。

```
┌────────────────────────────────────────────────────┐
│ 1 代码库本身：API 设计、架构、重构         确定性  │  ← 投入最多
└─┬────────────────────────────────────────────────┬─┘
  │ 2 静态分析：lint、类型系统、编译器、测试  确定性 │
  └─┬────────────────────────────────────────────┬─┘
    │ 3 验证：运行时验证、形式化验证、性质测试    │
    └─┬────────────────────────────────────────┬─┘
      │ 4 文字：rules、skills、AGENTS.md      │  ← 只放需要判断的
      └────────────────────────────────────────┘
```

### 第 1 层：代码库是 agent 最大的输入

agent 的输出取决于输入，而代码库是最大的输入。代码库里的 workaround、反模式、废弃代码和技术债，下一个 agent 会当成“既定模式”照抄——像花园里的杂草，不知不觉就长满了。所以每次想往规则文件里加一行时，先想能不能把它变成代码里的确定性约束：可复现、在代码里，才值得信任。

她的例子（Grok Bot 的客户端框架 Dune，“Electron 版的 Next.js”）：

- **禁用需要细腻判断的 API**。React 的 `useEffect` 有正当用途，但极易误用，而 agent 不擅长这种细腻判断。办法是直接禁用，只允许在框架自己的 API 内部使用。这类问题从此“被整类消灭”，评审里再也不用找它。
- **用目录结构表达上下文**。Cursor 里常见的反模式是把主进程代码 import 进渲染进程，造成长任务和卡顿。Dune 约定两个顶层目录（main 与 renderer），二者互相 import 由依赖图分析器禁止。规则很简单，但评审时少想一件事。

### 第 2 层：每次纠正都变成 lint，错误信息要说清怎么修

- **agent 会用 Markdown 给自己开脱**：文档、代码注释、rules、skills 里写下“为什么不这样做”的理由，或者把一次小纠正过度泛化成永远不能违反的铁律。
- **注释是逃生舱**。Cursor 的例子：agent 大量使用 `setTimeout`、`requestAnimationFrame`、`requestIdleCallback` 作为快速修复，掩盖 VS Code 命令式风格与 React 声明式风格之间的架构冲突，还写注释说明“这个快速修复是合理的”。结果定时器四处蔓延，频繁创建销毁引发 GC，应用卡顿。
- **所以 Grok Bot 禁掉了 99% 的注释**：注释容易过时，人基本不读，还给 agent 留了“难，所以不做对的事”的借口；最糟的是注释无法强制执行。取而代之的是 lint 规则，**错误信息告诉 agent 去修根因，而不是打补丁**。
- **总原则**：每次纠正 agent，都变成这样一条确定性检查，或者想办法通过更好的 API 设计和架构从代码里整类消灭这个问题。做得足够多，评审要盯的东西就越来越少；到某个时候你会发现没什么可审的了，可以让 agent 自己合并大部分 PR。

### 第 3 层：评审变成看验证证据

她们的代码评审已经缩成了查看验证产物：视频、截图。

- **运行时验证**：让 agent 自己运行代码，用人类开发者也用的调试工具（Chrome DevTools Protocol）。
- **功能地图（feature map）**：从用户视角列出应用里所有功能的快照。你说“左边栏那个东西”，agent 不用猜；人和 agent 有了共同词汇。
- **自定义 CLI 驱动**：agent 每次复用同一个驱动，省 token，而且驱动本身可测试。
- **形式化验证**：用 TLA+ 对主要用户流程做模型检查（如跨设备、跨平台的通知）；用 Lean 证明算法性质（自研虚拟列表库不闪烁、不抖动）。已经找到不少 bug，但不是银弹，只是环境里的又一层。
- **UI 的性质测试**：Bombadil，也已发现几个 UI bug。
- **状态图**：她的 `statechart` skill 把 TLA+ 模型画成用户视角的状态图，和视频、截图一起评审，比读规格容易。
- **token 去向**：她引用的一位工程师说自己 70% 的 token 花在验证上，她说自己的情况也类似。这些都不是新技术，只是以前太贵、难以理解或维护；agent 把成本打了下来，“软件测试的黄金时代”来了。

### 第 4 层：文字只放需要判断的

rules、skills、AGENTS.md 放在最后，只留给机器判断不了的事。

### 在建软件工厂之前

先改代码库，阻止反模式新增；再清理旧模式；然后把验证做扎实。这些本来就是自动化的前提：**内循环产出 slop，自动化之后只会产出更多 slop**，还得砸越来越多的 token。基础打好以后，外循环很容易搭：她的例子是每次切版本时自动起一批 agent，像真实用户一样 fuzz 整个应用，为找到的每个 bug 开修复 PR 并自动合并——之所以敢这样做，是因为代码库已经好到 PR 默认就是好的，大部分产品代码不再需要深度人审。

## pstack 里的对应做法

演讲里的原则在她公开的 pstack skills 里有可执行的版本，本仓库主要参考了这几个：

| skill | 做什么 |
|---|---|
| `correct` | 从提交、revert、评审意见里找出现两次以上的错误类；按 架构 → 类型 → lint/CI（错误信息点名该用的文件、类型或函数）→ 测试 → 文档 的顺序，在能做到的最高一层修；证明新检查在真实的过去错误上会失败；本地与 CI 用同一条命令；例外写在违规行上，带理由、到期日和人的批准；在 agent 指令文件里维护“规则 ↔ 由什么强制”的对照表 |
| `principle-encode-lessons-in-structure` | 第二次写同一条指令时，改成 lint、元数据、运行时检查或脚本；能结构化解决的，就只用结构化方案，“指令本身就是症状” |
| `no-comments` + Comment Sicko 子代理 | 删掉旁白、注释掉的代码、为 workaround 辩护的长注释；只放过许可证头、外部依赖强加的行为、公共 API 的文档注释、无法用代码表达的约束链接；我们自己代码里的“意外”标为 `MUST KILL`，交给重命名、类型或重构 |
| `create-verification-skill` | 为项目生成本地验证 skill：启动、自检、驱动、证据、清理，加一份功能地图（每个功能四节：子功能、如何到达、如何驱动、坑）；生成后必须实际跑通一个功能才算交付 |

### guard：确定性检查

一个只用标准库的 Python 脚本，Windows / macOS / Linux 同一条命令，本地、会话里和 CI 里都一样：

```bash
python scripts/guard.py                  # 检查；退出码 0 通过、1 有新违规、2 规则或配置有误（未完成检查）
python scripts/guard.py src/main/java    # 只查指定路径
python scripts/guard.py --list           # 列出规则、修法与来源
python scripts/guard.py --update-baseline   # 把基线缩小到当前件数（不会增加）
python scripts/guard.py --init-baseline     # 为尚未登记的规则一次性接受既有违规（由人执行，权限为 ask）
```

输出格式是 `文件:行: [规则ID] 修法`，下一行是违规的源码。示例（在示例应用的 Controller 里注入 Mapper）：

```
src/main/java/com/example/demo/OrderController.java:15: [java-no-field-injection] フィールドインジェクションを使わない。依存は private final フィールドにし、コンストラクタの引数で受け取る（コンストラクタが 1 つなら @Autowired は不要）。
    @Autowired
```

设计上对应演讲和 `correct` 的几条要求：

- **错误信息就是修法**。`message` 必填，写清该用什么（类、标签、方法），不是只说“违反了规则”。
- **规则要在真实错误上证明有效**。每条规则必须有 `examples.bad`（实际出现过的错误）和 `examples.good`（正确写法与容易误报的相似写法）。每次运行先自检：bad 必须命中、good 必须不命中，否则退出码 2。规则写坏了不会静默放行。
- **只拦新增，旧债只减不增**（ratchet）。规则引入时，由人用 `--init-baseline` 一次性接受既有违规；此后某文件某规则的件数超过基线即失败，修好的违规用 `--update-baseline` 收紧，不能回来。这对应“先阻止反模式新增，再清理旧模式”。
- **例外写在违规行上，带理由、期限和批准人**：`// guard:allow <规则ID> until=YYYY-MM-DD by=<批准人> -- <理由>`（JSP 用 `<%-- … --%>`）。期限最长 1 年，过期、缺项、规则不存在都算违规；没被用到的例外会提示删除。agent 不写例外，评审把新增例外视为阻断。

起始的 10 条规则，大多来自 AGENTS.md 里原本只有文字的规定，少数来自演讲：

| 规则 | 拦什么 | 来源 |
|---|---|---|
| `jsp-no-scriptlet` | JSP 中的 `<% %>`、`<%= %>`、`<%! %>` | AGENTS.md |
| `java-no-field-injection` | 字段上的 `@Autowired` / `@Inject` / `@Resource`（`src/main`） | AGENTS.md |
| `controller-no-persistence` | Controller import Repository / Mapper / DAO | AGENTS.md |
| `java-no-empty-catch` | 空 catch、只有注释的 catch | AGENTS.md |
| `java-no-print-stack-trace` | `e.printStackTrace()` | AGENTS.md |
| `test-no-disabled` | `@Disabled` / `@Ignore` 让测试变绿 | AGENTS.md |
| `java-no-thread-sleep` | 用 `Thread.sleep` 等待 | 演讲：定时器式快速修复 |
| `e2e-no-fixed-wait` | 浏览器测试里的 `waitForTimeout` | 演讲：定时器式快速修复 |
| `comment-workaround` | 为回避策辩护的注释（暂定、とりあえず、workaround、FIXME 等） | 演讲：注释是逃生舱 |
| `java-no-commented-out-code` | 注释掉的代码 | 演讲：禁注释 |

guard 与 ArchUnit、PMD 的分工：guard 不需要改 `pom.xml`，同一条命令覆盖 Java、JSP 和测试脚本，团队从纠正里长出来的规则加一条 JSON 即可；但它只做文本匹配。看依赖关系的规则交给 ArchUnit，需要解析 JSP 的规则交给 PMD，二者都跑在 `./mvnw verify` 里（见下文）。`correct` skill 按错误的种类选放在哪里。

### correct：纠正的标准流程

人纠正 agent、或同一条评审意见出现第二次时，agent 按 [`correct`](../templates/project/.claude/skills/correct/SKILL.md) 处理：

1. 把这次纠正写成一个“错误类”，收集证据（对话、评审意见、revert、`git log -S`）。已经写在 AGENTS.md 里却还发生，就是复发，必须落到机制上。
2. 在最高可行的一层解决：设计上消灭 → 类型与编译 → guard 规则（或项目已有的 ArchUnit）→ 测试 → 文字；选了较低一层要说明上一层为什么不行。
3. 写规则：`examples.bad` 放真实出现过的错误。
4. 既有违规少就同一个 PR 里另起提交修掉；多就请人执行 `--init-baseline`。
5. 证明有效：错误存在时退出码 1，修好后 0，两次输出都贴进报告。
6. 更新台账：在 AGENTS.md 对应规则后加 `〔guard: id〕`，错误信息已足够的文字规则直接删掉。

### 功能地图：共同词汇与可执行的手顺

`docs/feature-map/` 下一个功能一个文件，四节固定：子功能、到达方式、操作与确认、注意点。“操作与确认”里写的是能直接执行的命令（`htmx-check.mjs` 或画面试验的套件）和用户看得见的合格结果，证据存到 `target/evidence/<功能ID>/`。示例应用的 [S01 注文登録](../tests/fixtures/sample-app/docs/feature-map/S01-order-new.md) 是样例；CI 的端到端会从这个文件里取出命令逐条执行并检查截图，所以地图过期就会失败。

### 评审改为从证据开始

- code-reviewer 的第一项是“验证证据”：没有执行过的命令和结果，或者只有“已确认”的自述，都按没有证据处理；guard 没跑或不通过即不可合并；新增 `guard:allow`、基线件数增加、规则被删或放宽，标为需要人批准的阻断项。
- 评审还会把“AGENTS.md 写了却没被遵守”的规定、diff 里重复出现的同类问题，作为 guard 规则候选提出来（id、范围、pattern、修法），供下一次 `correct`。
- PR 模板把“验证证据”放在 diff 说明之后、其他内容之前。

## 结合开源资源

按金字塔每一层，在 GitHub 上挑了成熟项目，逐个核对了版本、许可证和源码里的规则或 API（2026-11-23）。三项已集成，其中前两项在示例应用上验证过；其余写明用途和没集成的原因。

| 层 | 项目（版本，许可证） | 补什么 | 处理 |
|---|---|---|---|
| 1 结构 | [TNG/ArchUnit](https://github.com/TNG/ArchUnit) 1.5.1，Apache-2.0 | 按编译后的依赖检查分层：同包引用、全限定名引用 guard 看不到 | **已集成**：[`ArchitectureTest.java`](../templates/project/src/test/java/ArchitectureTest.java)（安装时加 `--with-archunit`），3 条规则按 Spring 注解和类名判断层，与包名无关；`FreezingArchRule` 与 guard 基线语义相同（既有违规登记一次，只减不增，默认不允许自动建档） |

集成时验证到的三件事，都写进了模板与测试：

- **guard 与 ArchUnit 互补**：在示例应用里加一个同包的 `OrderRepository` 并在 Controller 里使用，因为没有 import，guard 显示 OK；ArchUnit 失败，并给出 3 处依赖（构造、字段、方法调用）和日文修法。
- **PMD 插件的陷阱**：`check` 目标内部会另起一次 `pmd` 目标，而这次运行拿不到 `<execution>` 里的配置，会退回“分析 Java、用默认规则”，于是 JSP 一个都没查、构建照样成功。配置必须放在 `<plugin>` 下；模板测试检查了这一点。
- **PMD 的误报与修法**：`<input value="<c:out value='${name}'/>">` 这种把 `<c:out>` 套在 HTML 属性里的常见写法会被判为未转义，因为 PMD 看不出属性里的标签。属性值改用 `${fn:escapeXml(name)}` 更直接，示例应用已改，规则的提示里也写明了。

## 日常怎么用

1. **写代码时**：改完运行 `python scripts/guard.py`，再跑测试与 `./mvnw verify`；画面改动按功能地图的手顺执行并留下截图。
2. **被纠正时**：先修，再走 `correct`。目标不是“记住”，而是让下一个 agent 写不出同样的错误。
3. **提 PR 时**：证据放最前；评审从证据开始读。
4. **复盘时**：用 [`workflow-retro`](../.claude/skills/workflow-retro/SKILL.md) 看同一类纠正是否再次出现；再次出现说明规则没覆盖到，或者应该上升到设计层。

## 刻意没做的事与剩余缺口

- **自动合并与外循环**：演讲本身的警告就是不要自动化一个还会产出 slop 的回路。导入方先满足这些前提再考虑：主要的错误类都已落到 guard 或设计上；画面验证在 CI 里跑；有 revert 率之类的质量度量。本仓库已有的 `claude-review.yml.example` 只做只读评审。
- **没有照搬“禁止 99% 注释”**：日本团队的 Javadoc、设计说明与审计习惯不同，模板只禁“为回避策辩护的注释”和“注释掉的代码”。要不要更进一步，由团队决定，做法是往 `rules.json` 里加规则。
- **文本匹配的边界**：guard 不懂语法，误报靠 `files` 范围和 `examples.good` 控制。同包引用已由 ArchUnit 补上，但它要求导入方在 `pom.xml` 加依赖；反射与生成的代码两者都查不到。
- **例外的“人批准”只是一个名字**：agent 技术上可以伪造。靠 PR diff 与评审发现，控制矩阵里记为缺口。
- **形式化验证与性质测试未内置**：TLA+、Lean 适合并发与状态机复杂的系统；对典型的表单类业务系统，先把运行时验证做扎实收益更大。jqwik、Bombadil 的定位见上表。
- **PMD 检查不到的转义漏洞**：直接写在 JSTL 标签体内的 `${...}`（例如 `<c:if test="...">${name}</c:if>`）会被 PMD 视为在标签库里而放过；JavaScript 上下文里的转义它也不管。
- **数字未核实**：3,000 / 11,000 PR、0.5% revert 率等是她的自述；转写稿是机器转写。
