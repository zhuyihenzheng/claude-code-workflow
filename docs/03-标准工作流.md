# 03 · 标准工作流

## 一个任务的标准回路（六步）

以下是参照官方 Best Practices 整理的工程流程；中大型任务可采用，小修按风险简化：

### 1. 探索（Explore）
- 新会话先用 Plan Mode（`Shift+Tab` 切换）或内置 Explore 子代理只读摸代码：相关类、调用链、既有同类实现；
- 需求不清时，先让 Claude **访谈你**：提问澄清边界，把结论写成 `SPEC.md`，然后**开新会话**照 spec 实施（spec 同时成为第 5 步 reviewer 的对照物）。

### 2. 计划（Plan）
- Plan Mode 出计划，`Ctrl+G` 可在编辑器里直接改计划再执行；
- 计划要落到文件级：改哪些文件、新增哪些测试、验收标准是什么；
- 复杂任务可用 `opusplan`：计划阶段用强模型，执行切回性价比模型。

### 3. 实现（Code）
- Prompt 要具体：点名文件、描述症状、定义"修好长什么样"、给参照样例（"follow the pattern in `OrderController`"）；有日志/截图直接给（`@文件`、粘贴截图）；
- 中大型功能走 TDD：先写失败测试 → 实现 → 测试转绿（这也是 Superpowers 等技能框架的铁律，与 JUnit 天然契合）；
- 小修小补不要走全流程，直接描述 + 验证即可，避免仪式过重。

### 4. 验证（Verify）——回路里最重要的一步
给 Claude 一个**可判定的 check**，并在 CLAUDE.md 里写明命令：
- 后端：`./mvnw -Dtest=XxxTest test` 定向测试 + `./mvnw -q compile`；
- 前端（HTMX/JSP）：起服务后用 Playwright 打开真实页面断言行为（见 [04](04-java-spring-htmx-jsp.md)）；
- **要求证据**：要命令输出/截图，不要接受口头"测试全过"。

强制程度阶梯（按任务风险选）：
1. prompt 里要求自验（最弱）；
2. `/goal <条件>`：独立模型每轮复核条件，适合无人值守长跑；
3. `Stop` hook 退出码 2 提供失败反馈，并设置超时、重试与失败出口；它不是最终合并门禁；
4. 新上下文 reviewer 复核（下一节）。

### 5. 复核（Review）
- 用**没参与编写的新上下文**做 reviewer：已安装的 code-review 插件/当前可用的评审入口、单独的 reviewer 子代理、或干脆开第二个会话（成本取决于模型、上下文与用量）；
- reviewer 的输入由调用方提供：基准提交 + 完整 diff（暂存、未暂存、新文件）+ SPEC/验收标准 + 测试结果；只读代理不能自行运行 git diff，缺输入时必须标注不完整；
- 社区进阶做法：planner / coder / reviewer 三角色分工，reviewer 只给只读工具（Read/Grep/Glob），在子代理定义里用 `tools:` 限定——这是 harness 强制而非自觉。

### 6. 提交（Commit / PR）
- 小步提交，提交信息说明"为什么"；PR 描述带验证证据（测试输出摘要、页面截图）；
- 走团队既定的 GitHub 流程（见 [06](06-团队协作与ci.md)）。

## 上下文管理

- 上下文窗口、压缩与缓存行为依模型/账号/版本而异；长上下文仍影响成本和质量，不把最大窗口当作所有会话的保证；
- 不相关任务之间 `/clear`；长会话用 `/compact <保留重点>`（注意 compact 本身也是一次大请求，别频繁用）；
- 侧问题用 `/btw`（不进历史）；`/context` 看上下文构成；用安装版本提供的用量入口与账单复盘，指标口径以实际界面为准；
- 纠正两次还不对：直接 `/clear` 重写 prompt，不要在烂上下文里继续吵（社区称 correction rabbit hole）；
- `/rewind`（或空 prompt 时 `Esc Esc`）回滚到 checkpoint：可分别还原代码/对话/两者。注意 Bash 改过的文件、多数 subagent 的编辑不在 checkpoint 追踪内，**它不是版本控制的替代品**，重要节点先 git commit。

## 子代理的使用纪律

- 价值在：并行、隔离噪音输出（大搜索、长日志）、独立复核；**不是**"换个 agent 答案更聪明"；
- 每个子代理都是一次独立请求，要重新收集上下文，未必更快、且与主会话共享用量池；
- 简单子代理在定义里钉 `model: haiku`；只给必要工具；`description` 写清"何时用我"，主会话靠它做委派判断；简单任务不默认拆代理。

## 并行开发

- 一个并行任务一个 worktree：`claude --worktree <name>`（或 Desktop 并排开会话）；
- gitignored 文件用仓库根 `.worktreeinclude` 声明复制清单；本地配置类大目录可用 symlink 设置；
- 每个 worktree 任务独立分支、独立 PR，注意端口、临时文件与数据库资源也要隔离。

## 无人值守 / 自动化（官方五问）

放它自己跑之前，五个问题都要有答案：
1. 它知道 "done" 长什么样吗？（goal / spec / 一条要转绿的失败测试）
2. 它能自检吗？（测试 / Stop hook / 评审步）
3. 它能碰什么？（permissions、`dontAsk` 模式、sandbox、指定 worktree 与可推分支）
4. 什么让它停？（`--max-turns` / `--max-budget-usd` / 组织 spend limit）
5. 结果去哪、谁签字？（PR + 人批准合并与发布）

脚本化配方：`claude -p "任务" --bare --allowedTools "..." --permission-mode dontAsk --output-format json --max-budget-usd N`。`--bare` 跳过 hooks/skills/plugins/MCP/CLAUDE.md 的自动发现，保证 CI 可复现，需要什么显式用 `--settings`、`--mcp-config` 传入。

Ralph 式 AFK 循环（社区 Geoffrey Huntley 2025 年提出：`while` 循环把 PROMPT.md 喂给全新上下文、状态全落盘）适合"规格已冻结的批量任务过夜跑"，官方 marketplace 里也有 ralph-loop 插件；团队在阶段 4 之后、有预算与回滚纪律时再试点，不要一上来就无人值守。
