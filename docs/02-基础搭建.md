# 02 · 基础搭建

## 1. 安装与基线

Java 团队可使用 Claude Code CLI + JetBrains 集成；VS Code、Desktop 或 Web 按工作环境选。按[官方安装文档](https://code.claude.com/docs/en/setup)安装，不复制不明来源的一键脚本。

记录 `claude --version`，用 `/status` 核对账号和模型、`/doctor` 排查环境。命令是否存在、权限默认模式与功能入口以安装版本的 `/help` 和官方文档为准。

## 2. 入库结构

- `AGENTS.md`：工具无关的项目规则，分“团队共通规则”与“本系统固有信息”。
- `CLAUDE.md`：首行 `@AGENTS.md` 导入，只追加 Claude Code 配置入口。
- `.claude/settings.json`：团队共享权限；模板没有 `hooks` 键，不启用任何 hooks。
- `.claude/hooks/verify-stop.py`：原样保留的可选 macOS/Linux/WSL 参考样例，未注册，不会在会话结束时运行；原生 Windows 需用户先改写。启用时由用户自行添加 Stop hook，示例见[模板说明](../templates/README.md)。
- `.gitattributes`：固定 `mvnw` / `*.sh` 为 LF、`*.cmd` 为 CRLF；与既有规则逐项合并。
- `.claude/rules/`：按路径加载的页面/后端规则。
- `.claude/agents/`、`.claude/skills/`：按需使用的 reviewer 与任务流程。
- `.mcp.json`：所需 MCP 配置；可选密钥只引用环境变量。
- `.github/workflows/`：按需启用的 GitHub 自动化。
- `.github/copilot-instructions.md`：引用 AGENTS.md 并保留必守摘要；`.github/instructions/`：由路径规则生成的 Copilot 镜像。
- `scripts/sync_rules.py`：从本手册复制的规则同步脚本，目标项目传入 `.`，用 `--check` 检查漂移。

`.claude/settings.local.json`、`CLAUDE.local.md` 与真实凭据不入库；已有项目逐项合并模板，不覆盖现有配置。当前版本的 AGENTS.md 支持条件见[官方 memory 文档](https://code.claude.com/docs/en/memory#agentsmd)，跨工具团队应验证实际加载了哪份指令。

## 3. Settings 分层

| 层级 | 位置 | 用途 |
|---|---|---|
| Managed | 组织管理配置 | 组织约束，优先级与例外见官方文档 |
| User | `~/.claude/settings.json` | 个人全局偏好 |
| Project | `.claude/settings.json` | 团队共享，入库 |
| Local | `.claude/settings.local.json` | 项目个人配置，不入库 |

不要假设数组与 hooks 会被本地设置简单覆盖；按[官方合并规则](https://code.claude.com/docs/en/settings)核对最终生效配置。JSON 中不要随意加入 `_comment`，尤其 `hooks` 下只能放支持的事件。

## 4. AGENTS.md 与工具入口规范

AGENTS.md 保持短而明确（模板目标少于 150 行，不是工具功能硬限制）：团队共通规则跨系统原样复制，真实构建/测试命令、部署方式、版本、样例与历史约定放入本系统固有信息。能从代码可靠获取的内容不要反复复制。

CLAUDE.md 用 `@AGENTS.md` 导入，仅保留 Claude Code 专属配置，见[官方导入说明](https://code.claude.com/docs/en/memory#import-additional-files)。把重复任务流程放入 skill；局部约定放入带 `paths:` 的 rules。路径规则在 Claude 读到匹配文件时也可能加载，不仅在编辑时加载。编辑 rules 后运行同步脚本生成 Copilot 镜像；各 Copilot 入口是否读取 AGENTS.md、支持哪些指令，以 GitHub 官方文档为准，步骤见[模板说明](../templates/README.md#规则维护与-copilot-兼容范围)。定期检查过时命令、互相矛盾的约定和不存在的样例路径。

## 5. 权限与安全边界

1. 按团队风险明确选择权限模式，不能依赖某版本的默认值。默认不使用 bypassPermissions；隔离环境也不应暴露生产凭据。
2. deny 在其匹配的权限检查中优先于 allow，但**不是所有代码执行路径的访问控制**。Read/Edit 路径规则对内置工具与部分可识别 shell 操作有效，任意 Python/Node 子进程、MCP 与 hook 需要独立管控；mods 还可能改变权限判定，见[官方 permissions](https://code.claude.com/docs/en/permissions)。
3. Bash 字符串规则不能穷举命令变体；`Bash(./mvnw *)` 也会放开 deploy 与插件目标。只预授权需要的命令，且只对可信仓库执行构建。
4. `/sandbox` 的 OS 级文件/网络限制与工具权限互补；不要假设 MCP 与所有文件工具自动落在 Bash 沙箱内。组织安全策略应使用 managed settings、运行环境隔离与最小凭据共同落实。
5. 项目 `.claude/settings.json` 中的 `/path` 锚定主工作目录，而非 `.claude`；应从项目根/worktree 根启动。`./path` 随当前目录变化；`--settings` 指定文件的 `/` 则锚定该文件目录。`/**/.env` 与 `/**/.env.*` 已覆盖根和嵌套目录，不需重复根规则。真实敏感目录还需按项目补充。
6. 迁移目录 blanket deny 会同时禁止新增文件。本模板使用 ask；禁止篡改已合并迁移仍需迁移校验与 CI。

Windows 权限路径仍写正斜杠 `/`：[官方权限文档](https://code.claude.com/docs/en/permissions#how-path-patterns-match)说明 Windows 路径会先规范化为 POSIX 形式再匹配；项目内 `/**/.env` 等规则保持原样。真实 Windows CLI 的拦截行为仍待验收。`PowerShell(...)` 语法已获[官方文档](https://code.claude.com/docs/en/permissions#powershell)确认，模板提供 `.\mvnw.cmd` 的精确 allow；旧版 CLI 是否有此工具以官方文档及安装版本为准。原有 Bash deny 保留，其命令规则只匹配 Bash；PowerShell 或任意脚本需分别评估。

模板行为、Python/平台要求与验证命令见 [templates/README.md](../templates/README.md)。

## 6. Windows 两条路径

### A. WSL2（推荐）

在 WSL2 内安装并运行 Claude Code、Git、JDK、Python 和 Node.js，项目也 clone 到 WSL 文件系统（如 `~/work/project`），不要放在 `/mnt/c` 下再用 Linux 工具构建；跨文件系统访问会增加开销，见 [Microsoft 文件系统建议](https://learn.microsoft.com/en-gb/windows/wsl/filesystems)。使用 `./mvnw` 与 `python3`，手动完成编译、测试和 verify。参考 hook 即使在 WSL 中也默认不启用。

### B. 原生 Windows

1. **Git for Windows / Git Bash**：本模板的 Bash 工具路径需要安装 [Git for Windows](https://git-scm.com/downloads/win)。当前[官方安装文档](https://code.claude.com/docs/en/setup#windows)已允许无 Git Bash 时使用 PowerShell 工具；较旧版本及实际工具可用性以官方文档为准。用 `/doctor` 检查 Git Bash 检测情况，必要时按官方说明设置 `CLAUDE_CODE_GIT_BASH_PATH`。从项目根启动 Claude Code。
2. **JDK 与 Maven Wrapper**：安装项目要求的 JDK，设置 `JAVA_HOME` 指向 JDK 根目录，并将其 `bin` 加入 PATH；重新打开终端，检查 `java -version` 和 `mvnw.cmd -version`。目标项目需已有 `pom.xml`、`mvnw.cmd` 及其 wrapper 配置。CMD 用 `mvnw.cmd -q compile` / `mvnw.cmd test` / `mvnw.cmd verify`；PowerShell 加 `.\`，Git Bash 加 `./`。JDK 安装方式与具体路径以所用发行版官方文档为准。
3. **Python 命令**：仓库测试用 `py -m pip install -r requirements-dev.txt`、`py -m unittest discover -s tests -v`；没有 `py` 时用已安装的 `python`，不要直接照抄 `python3`。先检查 `py --version` / `python --version`。若命令打开 Microsoft Store 或指向错误解释器，检查 Windows 的“管理应用执行别名”（App Execution Alias）与 PATH，确保指向实际安装；入口和别名行为随安装方式而变，以 [Python 官方文档](https://docs.python.org/3/using/windows.html)为准。安装 Python 不会让 POSIX 参考 hook 支持 Windows。
4. **换行**：合并模板 `.gitattributes` 的以下规则，避免 shell wrapper 因 CRLF 失败、Windows 批处理换行漂移。它控制 Git 的文本规范化与检出，含义见 [Git 官方文档](https://git-scm.com/docs/gitattributes)。已有文件的换行调整单独审查，避免混入大量无关改动。

   ```gitattributes
   mvnw text eol=lf
   *.cmd text eol=crlf
   *.sh text eol=lf
   ```

5. **长路径**：在目标仓库运行 `git config core.longpaths true`，并优先使用较短的 checkout 路径。该选项针对 Git for Windows 的部分操作，不能保证 Java、Node 或其他工具都支持长路径，见 [Git for Windows 说明](https://gitforwindows.org/git-cannot-create-a-file-or-directory-with-a-long-path.html)；系统策略与各工具限制以官方文档为准。
6. **MCP**：原生 Windows 的 `npx` server 若启动失败，可能需 `cmd /c npx ...` 包装；仅调整 Windows 的目标配置，参数示例见[模板说明](../templates/README.md)。WSL/macOS/Linux 保留原 `npx` 命令。

本仓库不是 Java 工程，无法验证上述 JDK、Maven、MCP 和 Claude Code 会话在真实 Windows 上的组合；CI 只验证模板内容。Stop 参考脚本依赖 `/bin/sh`、POSIX 信号和进程组，在原生 Windows 跳过整个 `tests/test_hooks.py`，保留脚本供用户改写，模板其他测试照常运行。
