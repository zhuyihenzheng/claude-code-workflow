# 02 · 基础搭建

## 1. 安装

| 表面 | 说明 |
|---|---|
| CLI | 功能最全，所有配置的事实源。团队成员必装 |
| IntelliJ IDEA 插件（JetBrains） | 在 IDE 终端运行 CLI，带 diff 查看器、选区共享、diagnostics 同步——**Java 团队的主力入口** |
| VS Code 扩展 | 图形面板、内联 diff、计划以 Markdown 形式审阅 |
| Desktop | 可视 diff、并行多会话 |
| Web / 移动端 | claude.ai/code，适合查看与轻任务 |

装好后先跑两件事：`/status`（确认账号、模型实际版本、settings 生效来源）、`/doctor`（环境与配置体检，还能给出 CLAUDE.md 的删减建议）。

## 2. 仓库目录结构（提交进 git 的部分）

```
your-project/
├── CLAUDE.md                  # 项目指令（<200 行，见模板）
├── .claude/
│   ├── settings.json          # 团队共享设置：权限、hooks、模型默认值
│   ├── settings.local.json    # 个人覆盖（.gitignore，不入库）
│   ├── rules/                 # 路径作用域规则
│   │   ├── jsp.md             # paths: src/main/webapp/**/*.jsp
│   │   └── htmx.md
│   ├── agents/                # 项目子代理（如 code-reviewer）
│   └── skills/                # 项目技能（如 spring-endpoint）
├── .mcp.json                  # 项目级 MCP 配置（入库，密钥用环境变量引用）
└── .github/workflows/         # @claude / 自动评审 workflow
```

说明：
- `CLAUDE.md` 也可放在 `./.claude/CLAUDE.md`；无 CLAUDE.md 时 Claude Code 会读 `AGENTS.md`，但团队统一用 CLAUDE.md 做主文件。
- 子目录可以有自己的 CLAUDE.md / rules，进入该目录工作时按需加载，避免根文件膨胀。

## 3. Settings 分层

| 层级 | 文件 | 用途 |
|---|---|---|
| Managed（组织） | 控制台/MDM 下发 | 安全红线，不可被下层覆盖（企业场景） |
| User | `~/.claude/settings.json` | 个人全局偏好 |
| Project | `.claude/settings.json` | **团队共享，入库**：权限 allowlist、hooks、默认模型 |
| Local | `.claude/settings.local.json` | 个人覆盖，gitignore |

hooks 在多层级之间是**合并**而非覆盖——团队 hook 写在 project 层，个人不要在 local 层重复定义同名事件。

## 4. CLAUDE.md 规范（最重要的一节）

官方判据：**只写 Claude 看代码看不到的东西**。它能自己读代码找到、且真会去找的，一律删。

该写：
- 确切命令：构建、跑单个测试、起服务、格式化（写全命令，不要写"用 Maven 构建"）；
- 版本钉死：JDK、Spring Boot、Maven/Gradle 版本（也方便 Context7 按版本查文档）；
- 代码里会误导人的旧模式（"XxxAction 是遗留写法，新代码不要模仿"）；
- 仓库外决策：部署方式、异常处理规范、日志框架约定；
- 已经被纠正过两次的坑（Claude 的 Auto memory 也会自动记，但团队级的要人工沉淀到这里）。

不该写：架构总览、目录结构说明、通用语言规范（"写干净的代码"）、从文档能查到的 API 用法。

维护：目标 **<200 行**；多步流程搬进 skill；局部规则搬进 `.claude/rules/` 并用 `paths:` 限定作用域；定期跑 `/doctor prompt-audit` 查过时与冲突指令。

## 5. 权限与安全基线

- **权限模式**：新会话默认 auto mode（独立分类器审查 `curl|bash`、生产部署、force push、敏感数据外发等风险动作）。团队日常用 auto 或 manual；`bypassPermissions` 只允许在一次性容器里用。
- **deny 优先**：`permissions.deny` 在**包括 bypass 在内的所有模式**下生效。基线至少：
  - `Read` `.env*`、密钥与凭据文件；
  - `Bash` 危险命令（`rm -rf /` 类、直连生产库的命令）。
- **沙箱**：`/sandbox` 开 OS 级沙箱限制 Bash 的文件/网络。注意它**只覆盖 Bash**，文件工具与 MCP 在沙箱外——所以 MCP 的凭据作用域要单独管（见 05）。
- **密钥**：一律走环境变量，`.mcp.json` 里只写 `${VAR}` 引用；禁止把 token 写进任何入库文件。
